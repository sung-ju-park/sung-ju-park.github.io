02 Problem

PDF 문서에서 원하는 정보를 직접 찾아야 하는 번거로움

문서 내용을 근거로 질문에 답변해주는 서비스가 필요했습니다. 다만 외부 API에 문서를 보내지 않고, 로컬 LLM(Ollama)만으로 동작하도록 만드는 것을 원칙으로 삼았습니다 — API 비용 없이 자유롭게 실험하고, 문서 내용이 외부로 전송되지 않도록 하기 위해서입니다.

04 Technical Challenge

검색 결과가 부족해도 LLM이 그대로 답변을 생성해버리는 문제

기본 RAG는 검색 → 생성을 한 번만 거치는 단순 구조입니다. 검색된 문서가 질문과 잘 맞지 않아도, LLM은 그 문서를 근거로 삼아 부실하거나 부정확한 답변을 만들어낼 수 있다는 한계가 있었습니다.

단일 검색
→
검색 결과 불충분
→
그대로 답변 생성 (환각 위험)
05 Solution

이 문제를 모델 자체의 한계로 보지 않고, 검색 과정 자체를 개선해야 한다고 판단했습니다. LangGraph로 검색 결과가 질문에 답하기 충분한지 LLM이 스스로 채점(sufficient / insufficient)하고, 부족하면 질문을 검색에 더 적합한 형태로 재작성해 다시 검색하는 판단 루프를 추가했습니다 (최대 2회 재시도).

retrieve
→
grade_documents
→
충분 → generate
grade_documents
→
부족 → rewrite_query
→
retrieve (재시도)

정해진 파이프라인을 한 번 실행하는 일반 RAG와 달리, 결과에 따라 스스로 경로를 바꾸는 것이 이 구조와 일반 RAG의 핵심적인 차이입니다.

06 Result

단일 검색 구조에서, 검색 결과에 따라 다음 행동을 스스로 결정할 수 있는 Agent 구조로 확장했습니다. Streamlit UI에서 "일반 RAG"와 "Agent 모드"를 토글로 전환하며 두 방식의 답변을 바로 비교해볼 수 있도록 구성했습니다.

Agent 모드 — 문서에 있는 정보는 정확히 답변하고, 없는 정보는 지어내지 않고 솔직하게 답변합니다.

07 Architecture
PDF 업로드
↓
텍스트 추출 (PyPDFLoader) → 청크 분리 → 임베딩 (Ollama: nomic-embed-text)
↓
벡터 저장 (Chroma)
↓ 질문 입력 시
벡터 유사도 검색 → grade_documents
충분 → LLM(qwen2.5:3b) 답변 생성
부족 → 질문 재구성 → 재검색

이 RAG 로직은 이후 MCP 서버로도 그대로 재사용되어, Claude Desktop이 HTTP 계층 없이 파이썬 함수를 직접 호출하는 구조로 확장되었습니다 (search_documents, ask_document_agent, upload_document).
