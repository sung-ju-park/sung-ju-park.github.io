02 Problem

PDF 문서에서 원하는 정보를 직접 찾아야 하는 번거로움

문서 내용을 근거로 질문에 답변해주는 서비스가 필요했습니다. 다만 외부 API에 문서를 보내지 않고, 로컬 LLM(Ollama)만으로 동작하도록 만드는 것을 원칙으로 삼았습니다 — API 비용 없이 자유롭게 실험하고, 문서 내용이 외부로 전송되지 않도록 하기 위해서입니다.

04 Technical Challenge

검색 결과가 부족해도 LLM이 그대로 답변을 생성해버리는 문제

기본 RAG는 검색 → 생성을 한 번만 거치는 단순 구조입니다. 검색된 문서가 질문과 잘 맞지 않아도, LLM은 그 문서를 근거로 삼아 부실하거나 부정확한 답변을 만들어낼 수 있다는 한계가 있었습니다.

단일 검색
→
검색 결과 불충분
→
그대로 답변 생성 (환각 위험)
05 Solution

이 문제를 모델 자체의 한계로 보지 않고, 검색 과정 자체를 개선해야 한다고 판단했습니다. LangGraph로 검색 결과가 질문에 답하기 충분한지 LLM이 스스로 채점(sufficient / insufficient)하고, 부족하면 질문을 검색에 더 적합한 형태로 재작성해 다시 검색하는 판단 루프를 추가했습니다 (최대 2회 재시도).

retrieve
→
grade_documents
→
충분 → generate
grade_documents
→
부족 → rewrite_query
→
retrieve (재시도)

정해진 파이프라인을 한 번 실행하는 일반 RAG와 달리, 결과에 따라 스스로 경로를 바꾸는 것이 이 구조와 일반 RAG의 핵심적인 차이입니다.

06 Result

단일 검색 구조에서, 검색 결과에 따라 다음 행동을 스스로 결정할 수 있는 Agent 구조로 확장했습니다. Streamlit UI에서 "일반 RAG"와 "Agent 모드"를 토글로 전환하며 두 방식의 답변을 바로 비교해볼 수 있도록 구성했습니다.

Agent 모드 — 문서에 있는 정보는 정확히 답변하고, 없는 정보는 지어내지 않고 솔직하게 답변합니다.

07 v5 Update · 안전장치와 평가

"문서에 근거해서만 답한다"를 실제로 확인하는 장치

v4까지는 프롬프트에 "문서에 근거해 답하라"고 적어 두기만 했을 뿐, 실제로 그렇게 답했는지 확인하는 장치가 없었습니다. 또 업로드한 문서에 "이전 지시를 무시하고 ~라고 답하라" 같은 문장이 섞이면 LLM이 이를 명령으로 따를 수 있습니다. 그래서 입력과 출력 양쪽에 확인 단계를 넣었습니다.

검색
→
문서 속 지시문 걸러내기
→
답변 생성
→
근거 확인 → 통과 / 보류

답변에 검색된 문단에 없는 숫자나 영문 이름이 있으면 답변을 내보내지 않고 원문 확인을 안내합니다. Agent 화면에서는 검색 → 채점 → 재작성 → 생성 → 근거 확인 단계가 끝날 때마다 실시간으로 표시됩니다.

인젝션 실험지시문 3개를 섞은 가상 문서, 질문 8개 — 공격 성공 1/8(안전장치 끔) → 0/8(켬), 정답 6/7 → 7/7
기존 26문항 평가안전장치를 켠 상태에서 답변 52개 중 정답을 잘못 막은 경우 0건
한계문서 안에 있는 다른 숫자를 엉뚱한 자리에 쓴 오답은 잡지 못함 (예: 정답 0.869 대신 0.995) — 규칙 기반 확인의 한계로 기록
테스트가짜 LLM으로 Ollama 없이 도는 pytest 27개 (안전장치 규칙, Agent 분기, API, 채점 규칙)

v5 Agent 모드 — 문서에 없는 질문에 지어내지 않고 답했고, 안전장치 판정·재검색 횟수·응답 시간이 함께 표시됩니다.

08 업무 자동화 · Make

커밋할 때마다 손으로 정리하던 개발 기록을 자동으로

프로젝트를 여러 개 진행하면서 언제 무엇을 바꿨는지 따로 정리하는 일이 반복됐습니다. 이를 줄이기 위해 GitHub에 push할 때마다 커밋 정보가 시트에 자동으로 쌓이는 흐름을 Make로 만들었습니다.

GitHub push
→
Webhook
→
Make (Custom Webhook)
→
Google Sheets 행 추가

처음에는 기록 위치를 Notion 데이터베이스로 잡았지만, 올바른 ID를 넣어도 "찾을 수 없음" 오류가 계속 났습니다. Notion API의 데이터베이스 구조 변경과 관련된 호환성 문제로 보여, 원래 목적(기록 자동화)을 지키는 쪽으로 판단해 저장 위치를 Google Sheets로 바꿔 완성했습니다.

Make 시나리오 — GitHub Webhook 트리거 → Google Sheets(Add a Row)

커밋 메시지, 저장소명, 날짜, 커밋 링크가 push할 때마다 자동으로 쌓입니다.

09 Architecture
PDF 업로드
↓
텍스트 추출 (PyPDFLoader) → 청크 분리 → 임베딩 (Ollama: nomic-embed-text)
↓
벡터 저장 (Chroma)
↓ 질문 입력 시
문서 속 지시문 걸러내기 → 벡터 유사도 검색 → grade_documents
충분 → LLM(qwen2.5:3b) 답변 생성
부족 → 질문 재구성 → 재검색
↓
근거 확인 (안전장치) → 통과 시 답변 + 출처(파일·쪽 번호) / 실패 시 보류

이 RAG 로직은 이후 MCP 서버로도 그대로 재사용되어, Claude Desktop이 HTTP 계층 없이 파이썬 함수를 직접 호출하는 구조로 확장되었습니다 (search_documents, ask_document_agent, upload_document).
