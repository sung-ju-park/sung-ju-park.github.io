02 Problem

장애가 생겼을 때 사람이 일일이 확인하는 대신, 시스템이 스스로 진단하는 구조

시스템에 이상이 생겼을 때 누군가 계속 화면을 들여다보고 있어야 한다면 장애 대응이 늦어질 수밖에 없습니다. 호스트·트리거·알림이 유기적으로 연결된 모니터링 체계를 직접 구축하고, 그 알림이 정말로 동작하는지까지 확인하고 싶었습니다.

03 My Role

My Contribution

  • Docker Compose로 Zabbix 모니터링 스택(서버 / DB / 웹UI / 에이전트) 구성
  • Zabbix REST API를 활용한 호스트·템플릿 등록 자동화 스크립트(Python) 개발
  • CPU 부하 테스트를 통한 임계치 트리거·알림 동작 검증
04 Technical Challenge

트리거를 설정해두는 것과, 그게 실제로 동작하는 것은 다른 문제입니다

웹 UI에서 호스트와 트리거를 하나씩 수동으로 등록하는 방식은 호스트가 늘어날수록 반복 작업과 실수 가능성이 커집니다. 또한 트리거·알림 설정을 마쳤다고 해서 실제 장애 상황에서 정말로 알림이 오는지는 별개의 문제라는 점도 검증이 필요했습니다.

수동 호스트/트리거 등록
→
호스트 늘어날수록 반복 작업·실수 위험
05 Solution

Zabbix REST API를 활용해 호스트·템플릿 등록을 스크립트 한 번 실행으로 처리하도록 자동화했습니다. 이어서 실제로 CPU 부하를 발생시키는 테스트를 통해, 설정해둔 임계치 트리거가 정확한 시점에 작동하고 알림까지 이어지는지 end-to-end로 직접 검증했습니다.

REST API 등록 스크립트 작성
→
CPU 부하 테스트 실행
→
트리거·알림 동작 확인
06 Result

수동 등록 없이 스크립트만으로 호스트·템플릿을 등록할 수 있는 구조를 만들었고, 무엇보다 "설정해뒀으니 될 것이다"에서 멈추지 않고 실제 부하를 걸어 트리거·알림이 진짜로 동작하는지 직접 확인했습니다. 설정과 검증을 분리하지 않고 함께 확인하는 습관을 이 프로젝트에서 익혔습니다.
